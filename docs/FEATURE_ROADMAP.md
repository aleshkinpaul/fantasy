# Roadmap развития FR Fantasy

Документ фиксирует согласованный порядок новых функций после запуска Ла Лиги 2026–27. Порядок считается приоритетным: следующая крупная функция начинается после приемки предыдущей, но общие модели данных создаются заранее, если они нужны нескольким пунктам.

## Зафиксированный порядок

1. таймлайн турниров на главной странице;
2. список участников конференции;
3. попап составов, базовый матч-центр и предматчевые котировки;
3a. внепланово: обзор статистики тура в разрезе конференции или лиги;
4. титулы и иконки действующих чемпионов;
5. профиль участника с историей;
6. отдельный Зал славы;
7. форма команды и история личных встреч;
8. расширение матч-центра после появления новых полей API.

## Общие архитектурные решения

### Единый каталог турниров

Главная страница, титулы, профили и Зал славы не должны иметь независимые списки соревнований. Перед реализацией таймлайна создается единый локальный каталог, например `src/assets/data/tournaments.json`.

```ts
interface TournamentCatalogItem {
  id: string;
  period: string;            // "2026–27"
  yearStart: number;
  kind: 'la-liga' | 'cup' | 'champions-league' | 'summer';
  title: string;
  route: string;
  status: 'scheduled' | 'active' | 'completed';
  description?: string;
}
```

Статус завершенности должен быть явным. Нельзя определять архивность только сравнением года с текущей датой: летний турнир может закончиться, пока следующий сезон уже активен, а турнир может быть остановлен или перенесен.

Группировка выполняется по футбольному сезону:

- КЧМ-2025 завершает период 2024–25;
- ЧМ-2026 завершает период 2025–26;
- Ла Лига 2026–27 открывает период 2026–27.

### Стабильная идентичность участника

Для профилей, титулов и истории основной сущностью считается участник с внутренним стабильным `participantId`. Один человек может сменить аккаунт и получить несколько внешних `profileId`, поэтому использовать текущий `profile.id` как постоянный ключ истории нельзя. Связь аккаунтов хранится в отдельном версионируемом реестре и подтверждается вручную: совпадение имени само по себе не является основанием для объединения.

```ts
interface ParticipantIdentity {
  participantId: string;
  displayName: string;
  primaryProfileId: string;
  profileIds: string[];
}

interface ParticipantSeasonEntry {
  participantId: string;
  sourceProfileId: string;
  tournamentId: string;
  teamId?: string;
  teamTitle: string;
  teamLogo: string;
}
```

Build-скрипты сначала преобразуют каждый `sourceProfileId` в `participantId`, а затем агрегируют результаты. Исходный профиль сохраняется у каждого участия для аудита. Если два связанных аккаунта встречаются в одном турнире, скрипт должен потребовать явного правила объединения и не складывать показатели автоматически, чтобы не задвоить матчи и ФО.

### Исторические snapshots

Сайт не должен строить всю историю, запрашивая при каждом открытии старые внешние API. После завершения турнира создается локальный итоговый snapshot:

```text
src/assets/data/history/{tournamentId}.json
```

Он содержит участников, итоговые места, результаты H2H, ФО, кубковые результаты и призовые показатели. Для актуального турнира данные продолжают рассчитываться из API; после завершения результат фиксируется скриптом и проверяется перед переводом статуса в `completed`.

### Snapshots прогнозов

Предматчевые котировки нельзя пересчитывать задним числом по уже известным результатам. Для каждого тура до его начала сохраняется неизменяемый snapshot:

```text
src/assets/data/forecasts/{tournamentId}/tour-{tour}.json
```

Запись содержит идентификаторы матча и участников, время генерации, версию алгоритма, использованные туры, рейтинги формы, три вероятности исхода, уверенность, происхождение (`published` или `reconstructed`) и контрольный hash входных данных. Так опубликованный прогноз не изменится после обновления API или алгоритма, а восстановленный расчет нельзя спутать с реально опубликованной до матча котировкой.

## 1. Таймлайн турниров на главной странице

**Статус:** реализовано 29 августа 2026 года.

### Пользовательский сценарий

Главная страница показывает вертикальный таймлайн от новых периодов к старым. Каждый период имеет отдельный заголовок, например `2026–27`, и собственную группу турниров.

Порядок внутри периода фиксирован:

1. Ла Лига;
2. Кубок, если он разыгрывался;
3. Лига чемпионов;
4. летний турнир: КЧМ или чемпионат мира.

Турниры со статусом `active` визуально заметнее и имеют метку «Идет сейчас». `Completed` оформляются спокойнее, получают метку «Завершен» и считаются архивными. `Scheduled` можно показывать с меткой «Скоро», но без активной ссылки, пока страница не готова.

### Реализация

1. Создать типы и `TournamentCatalogService`.
2. Перенести все ссылки из `main-page.component.html` в каталог.
3. Добавить проверку уникальности `id`, корректности route, периода, статуса и порядка.
4. Построить view model: сортировка периодов по `yearStart` убыванию, турниров — по `kind`.
5. Заменить набор кнопок динамической разметкой таймлайна в `MainPageComponent`.
6. Добавить desktop-таймлайн и компактную mobile-версию.
7. Для Кубка использовать ссылку на кубковую вкладку соответствующей Ла Лиги, пока у него нет отдельной страницы.

### Критерии готовности

- новый турнир добавляется одной записью каталога без правки HTML;
- периоды всегда отсортированы от нового к старому;
- внутри периода соблюдается установленный порядок;
- отсутствующий Кубок не оставляет пустого места;
- завершенные турниры отличаются от активных не только цветом, но и текстовой меткой;
- все существующие маршруты с главной страницы продолжают открываться.

## 2. Участники конференции

**Статус:** реализовано 29 августа 2026 года.

### Пользовательский сценарий

После сабтаба «Матчи» появляется сабтаб «Участники». Для конференции из 16 команд он показывает сетку `4 × 4`:

- крупный логотип;
- название фэнтези-команды;
- имя участника;
- ссылку на внешнюю команду, а после появления профилей — на внутренний профиль.

На узких экранах сетка становится двухколоночной, затем одноколоночной. Порядок участников должен совпадать с порядком в конфигурации конференции, а не с текущей таблицей.

### Реализация

1. Зарезервировать `confTabId = 4`.
2. Создать standalone-компонент `ConferenceParticipantsComponent`.
3. Передавать в него `stage.leagues[confId].profiles` и общий индекс профилей.
4. Выделить переиспользуемый `ParticipantCardComponent`, который затем используется в профиле и Зале славы.
5. Добавить пустое состояние и проверку отсутствующих профилей/логотипов.

### Критерии готовности

- в каждой конференции отображаются ровно ее 16 участников без дублей;
- desktop-сетка имеет четыре колонки;
- подписи не перекрывают логотипы и корректно сокращаются;
- смена конференции обновляет список без дополнительного запроса API;
- прямой URL с `confTabId=4` восстанавливает выбранный экран.

## 3. Попап составов, базовый матч-центр и котировки

Статус на 29 августа 2026 года: реализована первая рабочая версия. Попап открывается по сопернику в расписании и по строке счета на вкладке матчей; показывает составы, запас, капитана/вице-капитана и расчет вероятностей. Для туров 1–3 Ла Лиги 2026/27 сохранены явно помеченные восстановленные расчеты, для еще не начавшегося 4-го тура — опубликованный предматчевый snapshot. Реестры реальных клубов и их эмблем остаются отдельным следующим этапом этой функции.

### Первая версия матч-центра

Клик по сопернику в расписании или по матчу открывает модальное окно. Оно показывает:

- хозяев и гостей, счет или время начала;
- основной состав и запас обеих команд;
- капитана и вице-капитана;
- позиции, стоимость и реальный клуб футболиста;
- общую стоимость состава;
- предматчевые вероятности исходов;
- статус прогноза: предварительный, зафиксированный, восстановленный или недоступный.

Модальное окно должно поддерживать клавиатуру, закрытие по `Escape`, возврат фокуса и блокировку прокрутки фона.

### Источники данных

- `full_info.data.players[profileId].team.rosters_by_tour[tour]` — основа, запас, капитан и вице-капитан;
- `sport_players_tour_stat` — имя футболиста, позиция, `team_id`, цена, `score` и `match_time`;
- локальный справочник реальных клубов — название и эмблема;
- forecast snapshot — опубликованные до тура котировки.

Загрузка подробностей должна быть ленивой: страница турнира не обязана заранее строить карточки всех футболистов. Нужен `MatchCenterFacade` с кэшем по ключу `competition + season + tour`.

### Алгоритм котировок `rating-softmax-v2`

Для матча тура `N` запрещено использовать данные тура `N` и более поздних туров. Единственная оценка силы команды — существующий рейтинг формы на конец тура `N - 1`. Он рассчитывается общей функцией рейтинга сайта:

- берутся до пяти последних доступных туров с весами `19, 15, 12, 10, 9`;
- ФО команды в каждом туре сравниваются с медианой этого тура;
- взвешенный результат нормализуется между результатами, которые дали бы минимальные и максимальные ФО каждого тура;
- итоговый рейтинг ограничивается диапазоном `0…10`.

Разность рейтингов ослабляется коэффициентом `min(1, число_туров / 5)`, поэтому один удачный тур не создает ложной уверенности. Затем три исхода переводятся в вероятности через softmax. Калиброванные параметры: сила разности рейтингов `0.40`, базовый логит ничьей `-0.90`; дополнительный штраф ничьей за разницу рейтингов не используется, поскольку данные его не подтвердили. `drawGap` соревнования корректирует вероятность ничьей.

Параметры подобраны на 1245 матчах завершенных турниров 2025/26. При проверке на последних 20% туров каждого турнира модель дала точность `55.12%` и log loss `0.9379`; на всей выборке log loss составил `0.9794` против `1.0241` у нейтрального baseline. Калибровка воспроизводится командой `npm run forecast:calibrate`.

Перед началом тура запускается `npm run forecast:snapshot -- <type> <yearStart> <tour>`. Скрипт использует ту же TypeScript-функцию расчета, что и интерфейс, и не позволяет менять snapshot после появления тура в API. Пока тур не начался, старую версию алгоритма можно заменить с архивированием прежнего файла:

```bash
npm run forecast:snapshot -- spain 2026 4 --replace-before-start
```

Для старых матчей без опубликованных котировок допустим только явно помеченный backfill. Он использует данные строго до нужного тура и показывается пользователю как «Восстановлено»:

```bash
npm run forecast:snapshot -- spain 2026 1 --reconstruct
```

### Реальные клубы, эмблемы и флаги

Текущий API проверен на Ла Лиге 2026: футболист содержит только поля `id`, `name`, `amplua_id`, `team_id`, `cost`, `stat_by_tours`. Национальности, флага и эмблемы клуба нет.

Следовательно:

- **эмблемы реальных клубов нужно подтянуть и хранить отдельно** в версионируемом справочнике по `team_id`; это рекомендуется сделать для первой версии матч-центра;
- текущий `teams.json` можно использовать как основу структуры, но он относится к старому составу Ла Лиги, а `logo` в нем пустой; его нужно заменить сезонным справочником;
- **флаги стран также потребуют отдельного источника**, причем API не дает даже nationality id, поэтому понадобится внешний справочник `player id → страна`;
- флаги предлагается отложить: они менее важны для чтения состава и заметно дороже в сопровождении, чем 20 клубных эмблем.

Рекомендуемый scope первой версии: позиция + имя + клубная эмблема, без флага страны.

### Критерии готовности

- попап открывается из расписания и списка матчей;
- состав соответствует `rosters_by_tour` выбранного тура;
- капитан и запас визуально различимы;
- отсутствие футболиста в справочнике не ломает окно;
- прогноз не использует данные текущего или будущего тура;
- историческая котировка не меняется после результата матча;
- вероятности валидны и в сумме дают 100%;
- для первого тура предусмотрен честный нейтральный прогноз и низкая уверенность.

## 3a. Статистика тура по конференции или лиге

**Статус:** реализовано 29 августа 2026 года; расширение по очкам футболистов и `played` ожидает новые поля API.

Первая версия включает этапы 1–4 из плана ниже: статистику результатов, составов и решений участников, адаптивный интерфейс, переход из рейтинга матчей в матч-центр и сохранение выбранного режима в query-параметрах. Этап 5 остается запланированным и включится через capability после расширения внешнего API.

### Пользовательский сценарий

На вкладке «Матчи» после выбора тура появляется локальный переключатель «Матчи / Статистика тура». Второй экран сохраняет выбранные этап, конференцию или лигу и тур, поэтому статистика никогда не смешивает команды из разных групп. Кубковые встречи в этот раздел не входят.

Экран состоит из компактных тематических блоков. По умолчанию каждый рейтинг показывает пять строк; для статистики футболистов доступна кнопка «Показать всех». В заголовке всегда виден контекст, например `3 тур · Конференция Анчелотти · 16 команд`, а при неполных данных — фактическое покрытие, например `составы 15 из 16 команд`.

Для будущего тура показывается пустое состояние. Если API когда-нибудь начнет отдавать промежуточные результаты, такой расчет должен иметь заметную метку «Предварительно» и автоматически заменяться итоговым после закрытия тура.

### Метрики, доступные на текущих данных

#### Результаты команд

- **Топ-5 команд по ФО** — `results_by_tour[tour].tour_score` по убыванию;
- **выше ожиданий тура** — превышение ФО команды над медианой выбранной конференции или лиги;
- **ниже ожиданий тура** — наибольшее отрицательное отклонение от той же медианы;
- **самая результативная проигравшая команда** — максимальные ФО среди проигравших H2H-матч;
- **самая экономная победа** — минимальные ФО среди победителей.

Последние две метрики показываются как отдельные факты тура, а не как оценка качества команды.

#### Матчи

- **Топ-5 по результативности** — сумма ФО хозяев и гостей по убыванию;
- **топ-5 по упорности** — абсолютная разница ФО по возрастанию; при равенстве выше матч с большей суммой ФО;
- **крупнейшие победы** — разница ФО по убыванию;
- **неожиданный результат** — победа команды с наименьшей предматчевой вероятностью; метрика доступна только при реально опубликованном snapshot и не строится по восстановленной котировке.

Для ничьей используется уже существующее правило соревнования `drawGap`. В карточке матча отображаются обе команды, счет ФО, сумма или разница — в зависимости от рейтинга — и переход в матч-центр.

#### Выбор футболистов

- **самые популярные футболисты** — число составов из 15 игроков, в которых встречается футболист;
- **самые популярные в основе** — число попаданий в стартовые 11;
- **самые популярные капитаны** — число назначений капитаном;
- **волна покупок** — сколько участников добавили футболиста относительно предыдущего тура;
- **волна продаж** — сколько участников убрали футболиста относительно предыдущего тура;
- **популярные реальные клубы** — суммарное число выбранных футболистов клуба, отдельно можно показать долю в основе.

Популярность считается по числу загруженных составов выбранной конференции или лиги, а не по всем участникам турнира. Для каждого футболиста полезно показывать абсолютное значение и долю: `11 из 16 · 68,8%`. Повтор одного id внутри некорректного состава учитывается один раз и регистрируется валидатором.

#### Решения участников

- **самый активный менеджер** — больше всего новых футболистов относительно предыдущего тура;
- **самый стабильный состав** — меньше всего изменений относительно предыдущего тура;
- **самый оригинальный состав** — минимальная средняя популярность его 15 футболистов внутри лиги;
- **самый шаблонный состав** — максимальная средняя популярность состава;
- **самая оригинальная основа** — минимальная средняя популярность стартовых 11;
- **единоличные выборы** — число футболистов, которых больше никто в этой лиге не использовал.

Первый тур не участвует в рейтингах изменений состава. Переход запасного в основу не считается покупкой: покупка или продажа определяется по полному набору из 15 футболистов.

### Метрики после появления надежных очков и `played`

Эти показатели включаются только через явную capability API. Наличие числового `score` без надежного признака участия не должно молча активировать блок:

- лучшие футболисты тура по ФО и лидеры каждой позиции;
- лучший дифференциал — высокие ФО при низкой популярности;
- лучшее соотношение `ФО / стоимость`;
- самый эффективный капитан и суммарный капитанский бонус;
- самый неудачный популярный капитан;
- ФО, оставшиеся на скамейке, и «ошибка выбора основы»;
- оптимальный состав тура из реально сыгравших футболистов с учетом позиций;
- вклад футболистов реального клуба в суммарные ФО фэнтези-команд лиги.

Для первой реализации эти карточки не выводятся заглушками: интерфейс получает список доступных секций из результата расчета и показывает только подтвержденные данными метрики.

### Модель и правила расчета

Расчет оформляется чистой доменной функцией без Angular-зависимостей:

```ts
interface TourInsightsInput {
  tournamentId: string;
  tour: number;                 // абсолютный номер тура сезона
  stageName: string;
  leagueName: string;
  profileIds: string[];         // только выбранная конференция или лига
  matches: CompetitionMatch[];  // только матчи выбранной лиги и тура
  profiles: IProfileDetails[];
  sportPlayers: SportPlayer[];
  forecast?: ForecastSnapshotFile;
  capabilities: {
    playerScores: boolean;
    played: boolean;
  };
}
```

`calculateTourInsights(input)` возвращает готовые ранжированные view model без изменения `profiles`, `matches` или roster. Общие операции с составом — получение всех 15 id, основы, капитана и разницы двух туров — выносятся в переиспользуемые selectors, чтобы не дублировать логику матч-центра и призов.

Основные инварианты:

- абсолютный номер тура определяется через `stage.firstTour`, а не напрямую из индекса UI;
- в расчет попадают только `profileIds` текущей лиги;
- H2H-матч учитывается, только если оба участника входят в выбранную лигу; несовпадение считается ошибкой конфигурации;
- кубковые матчи не передаются калькулятору;
- все числовые значения API нормализуются в `number` на границе расчета;
- у каждого рейтинга есть стабильное правило разрешения равенства;
- отсутствие roster или карточки футболиста не ломает весь обзор и отражается в `coverage`;
- результаты не сохраняются вручную: для активного сезона они детерминированно строятся из уже загруженных данных, а после архивации могут входить в общий исторический snapshot турнира.

### Компоненты и поток данных

1. Добавить `tour-insights.models.ts` с типами результата и доступности секций.
2. Добавить `tour-insights-calculator.ts` с независимыми калькуляторами команд, матчей, популярности и поведения участников.
3. Выделить общие roster-selectors из существующей логики матч-центра.
4. В `LeagueH2HPageComponent` собирать контекст из активных `stage`, `league` и абсолютного тура. Дополнительных HTTP-запросов не требуется: squads, rosters и `sportPlayersByTour` уже загружены facade.
5. Создать standalone-компонент `TourInsightsComponent`. Он получает готовый результат, ничего не пересчитывает в шаблоне и эмитит открытие выбранного матча в существующий матч-центр.
6. Добавить локальный режим вкладки «Матчи / Статистика тура» в query state, чтобы ссылка восстанавливала этап, лигу, тур и выбранный экран.
7. Для длинных списков использовать единый компактный рейтинг: место, логотип, основная подпись, значение и вторичная расшифровка.
8. После появления новых полей API расширить только capability и player-performance calculator, не меняя контракт базовых секций.

### Этапы реализации

1. **MVP результатов:** топ команд, результативные, упорные и крупные матчи, факты о победителях и проигравших.
2. **Составы:** популярность всех 15, основы, капитанов, покупки и продажи.
3. **Участники:** активность, стабильность, оригинальность и шаблонность.
4. **Интерфейс:** переключатель, адаптивные карточки, переход в матч-центр, состояния загрузки и отсутствия данных.
5. **Расширение API:** очки футболистов, `played`, капитанский эффект, скамейка, дифференциалы и оптимальный состав.

### Тестирование и критерии готовности

- unit-тесты фиксируют формулы и tie-breakers каждой метрики;
- отдельные тесты проверяют второй этап с `firstTour > 1`, смену лиги и отсутствие смешивания участников;
- первый тур корректно скрывает покупки, продажи и активность;
- неполный roster уменьшает coverage, но не меняет знаменатель незаметно для пользователя;
- все матчи рейтинга открывают тот же матч-центр и тот же абсолютный тур;
- переключение тура, конференции и этапа обновляет статистику без нового запроса API;
- будущий тур не получает выдуманных итоговых значений;
- восстановленный прогноз не используется для звания «неожиданный результат»;
- существующие результаты матчей, таблицы, кубок, призы и рейтинги проходят сезонную регрессию без изменений;
- desktop и mobile версии не превращают обзор в длинную стену карточек: секции сворачиваются, а полный список открывается по запросу.

## 4. Титулы и иконки действующих чемпионов

### Модель данных

Результаты турниров хранятся отдельно от отображения иконок:

```ts
interface TournamentPlacement {
  tournamentId: string;
  participantId: string;
  place: 1 | 2 | 3;
  titleType: 'league' | 'cup' | 'champions-league' | 'world-cup' | 'club-world-cup';
}
```

Действующий чемпион определяется как победитель последнего завершенного турнира данного `titleType`. Это вычисляемое состояние, а не вручную проставленный флаг у участника.

### Отображение и реализация

1. Создать реестр типов титулов и их иконок.
2. Наполнить результаты завершенных турниров; неизвестные архивные результаты запросить у владельца проекта.
3. Создать `AchievementService` и переиспользуемый `TitleBadgeComponent`.
4. Показывать небольшую иконку возле логотипа в таблице, участниках и матчах, с tooltip названия и сезона.
5. Несколько действующих титулов объединять в компактную группу; полный список показывать в профиле.
6. После завершения нового турнира действующего чемпиона определять автоматически по каталогу.

## 5. Профиль участника с историей

Маршрут: `/participants/:participantId`.

Страница содержит имя и актуальную команду, прошлые названия и логотипы, титулы, участия по сезонам, итоговые места, H2H-баланс, ФО, кубковые достижения, специальные призы и ссылки на матчи.

### Реализация

1. Создать глобальный реестр участников с `participantId`, `primaryProfileId` и массивом подтвержденных `profileIds`.
2. Написать build-скрипт, который разрешает каждый внешний `profileId` в `participantId`, агрегирует сезонные файлы и исторические snapshots и сохраняет источник каждой записи.
3. Создать `ParticipantHistoryService` и standalone-страницу профиля.
4. Не загружать все внешние API прошлых сезонов при каждом открытии.
5. Постепенно заменить ссылки на внешнюю команду внутренними ссылками на профиль, сохранив внешнюю ссылку отдельной кнопкой.
6. Добавить валидатор реестра: один `profileId` принадлежит только одному участнику, `primaryProfileId` входит в `profileIds`, циклических alias-ссылок нет.
7. Для случая нескольких аккаунтов в одном турнире требовать явную стратегию (`continue`, `replace` или `separate`) и проверять отсутствие двойного учета матчей, ФО и титулов.

### Критерии готовности

- смена названия команды не создает нового участника;
- один участник объединяет Ла Лигу, Кубок, ЛЧ и летние турниры со всех подтвержденных аккаунтов;
- переход на новый аккаунт не разрывает историю, а исходные `profileId` остаются видимыми в технических данных;
- один матч, тур или титул не учитывается дважды при объединении аккаунтов;
- отсутствующие старые показатели показываются как «нет данных», а не как ноль;
- страница доступна по прямой ссылке после обновления браузера.

## 6. Зал славы

**Статус: реализовано 30 августа 2026.**

Отдельный маршрут `/hall-of-fame` показывает победителей и призеров, фильтры по соревнованию и периоду, количество чемпионств/финалов/призовых мест и действующих чемпионов.

Зал славы использует тот же `TournamentPlacement` и snapshots, что титулы и профили. Второй ручной список победителей создавать нельзя. Для архивных результатов, которых нет в локальных файлах, нужен однократный импорт данных от владельца проекта.

Критерий готовности: новый завершенный snapshot появляется в Зале славы без правки компонента, а каждый титул одинаково отображается в Зале славы и профиле.

Реализация использует единый реестр `src/assets/data/achievements.json` и runtime-валидатор в `AchievementService`. Компонент не содержит ручного списка победителей: он объединяет placements с завершенными записями `tournaments.json`. В реестре поддерживаются:

- несколько самостоятельных зачетов одного турнира — Примера и Сегунда Ла Лиги 2025/26;
- несколько обладателей одного места — два бронзовых призера ЛЧ 2025/26;
- командные placements — КЧМ 2025 показывается одной командой, а достижение засчитывается каждому участнику состава;
- стабильный `participantId` и несколько внешних `profileIds` одного человека; первым подтвержденным alias стал Иван Шураев (`1116146089`, `1116848369`);
- автоматически вычисляемые действующие чемпионы и личный рейтинг по числу титулов, финалов и пьедесталов.

В первом наборе данных представлены семь завершенных турниров и восемь зачетов сезонов 2024/25–2025/26. Переиспользование этих же placements в иконках титулов и будущих профилях остается частью пунктов 4–5, а не отдельным источником данных.

## 7. Форма и история личных встреч

### Форма

- последние пять H2H-результатов;
- средние набранные и пропущенные ФО;
- серии побед и без поражений;
- изменение рейтинга;
- стабильность результатов;
- форма по выбранному турниру и общая форма, если данные сопоставимы.

### Личные встречи

- количество матчей, побед, ничьих и поражений;
- суммарные и средние ФО;
- крупнейшая победа;
- последние встречи по датам;
- разбивка по турнирам и стадиям.

Для реализации выделяются `FormCalculator` и `HeadToHeadHistoryService`. Актуальные данные берутся из view model, прошлые — из snapshots. Компактный блок показывается в матч-центре, расширенный — в профиле. Эти же показатели позднее используются прогнозной моделью.

## 8. Расширение матч-центра после обновления API

Функция начинается после появления подтвержденного контракта API для признака участия футболиста и начисленных ему очков.

Планируемое отображение:

- индивидуальные ФО и сыгранные минуты;
- статус «не вышел»;
- признак учета в результате фэнтези-команды;
- вклад игрока и капитанский множитель;
- фактические замены основы и скамейки;
- сравнение прогноза с результатом;
- состояние live/incomplete/final.

Новые поля сначала добавляются как optional в API-модель. Adapter переводит внешний контракт во внутреннюю модель матч-центра, а UI включает блоки по наличию capability, а не по номеру сезона. Старые сезоны должны продолжить работать без новых полей.

## 9. Визуальное обновление архивных турниров без рефакторинга legacy-расчетов

**Статус:** реализовано 29 августа 2026 года.

Обновлены оба legacy-представления: общий `LeaguePageComponent` для архивных Ла Лиги и Лиги чемпионов и отдельный `CWCPageComponent`. Production-изменения ограничены их SCSS-файлами; TypeScript, HTML, данные и формулы не менялись. Контрольные DOM-хэши всех трех маршрутов совпали до и после редизайна.

### Цель и жесткие границы

Архивные страницы нужно привести к текущей светлой приглушенной палитре и общему визуальному языку сайта, сохранив их существующую структуру, данные и поведение. Это отдельная styling-only задача, а не продолжение рефакторинга доменного слоя.

В рамках задачи разрешено изменять только:

- `league-page.component.scss` для архивных Ла Лиги и Лиги чемпионов;
- `cwc-page.component.scss` для архивного Клубного чемпионата мира — отдельным вторым этапом после общей архивной лиги;
- общие SCSS-токены или mixins только при условии, что изменение не затрагивает внешний вид актуальных страниц; безопаснее использовать уже существующие токены без их переопределения.

Заморожены и не изменяются:

- `league-page.component.ts`, `cwc-page.component.ts` и все вызываемые ими методы расчета;
- HTML-шаблоны legacy-компонентов, порядок DOM-элементов и условия `*ngIf`/`*ngFor`;
- сервисы загрузки, модели, конфигурации турниров, локальные JSON и внешние API;
- сортировки, формулы рейтинга, таблицы, результаты матчей, медали, очки, призовые показатели и логика определения мест;
- актуальные страницы на `LeagueH2HPageComponent` и их стили.

Если желаемое визуальное решение требует нового поля, дополнительного класса в шаблоне или изменения вычисленного значения, оно откладывается: в этой задаче нельзя расширять scope за пределы SCSS.

### Маршруты и очередность

Первая очередь — страницы, использующие общий `LeaguePageComponent`:

1. `/spain?year=2024` — Ла Лига 2024/25;
2. `/champions-league?year=2024` — Лига чемпионов 2024/25.

Вторая очередь — `/club-world-cup?year=2024`, использующий отдельный и более сложный `CWCPageComponent`. Его оформление выполняется после фиксации визуальных правил на первых двух маршрутах.

Завершенные турниры 2025/26 на маршрутах с `/new` уже используют актуальный компонент и в этот этап не входят. Старый `CupPageComponent` также не входит в scope: архивные кубки 2025/26 открываются внутри актуальной страницы сезона.

### Визуальное направление

Архив сохраняет ту же базовую палитру, что актуальный сайт: светлый бежево-серый canvas, почти белые поверхности, синие акценты и нейтральные границы. При этом он выглядит спокойнее активного сезона:

- меньше насыщенных заливок и теней;
- синий используется для навигации и выбранного состояния, но не конкурирует с данными;
- зеленый, красный и серо-бежевый остаются семантическими цветами результатов;
- золото, серебро и бронза используются только для мест и медалей;
- логотипы размещаются на нейтральной подложке, чтобы одинаково читались темные и светлые изображения;
- плотность таблиц остается высокой, но строки получают ясное вертикальное разделение и устойчивую сетку числовых колонок.

### Этап 0. Фиксация исходного состояния

До изменения стилей нужно создать временный визуальный и структурный baseline для каждого маршрута:

- desktop `1440 × 1200`, tablet `768 × 1024` и mobile `390 × 844`;
- полный скриншот основной таблицы и каждого доступного представления/таба;
- список заголовков, количество строк и текст всех числовых ячеек;
- выбранные вкладки и видимость мобильных колонок;
- ошибки браузерной консоли.

Baseline нужен только для проверки и не становится новым источником турнирных данных.

### Этап 1. Общая оболочка архивных лиг

В `league-page.component.scss`:

1. Перевести фон, таблицу, границы, тени и типографику на существующие дизайн-токены проекта.
2. Оформить таблицу как цельную светлую поверхность с читаемым заголовком и спокойным hover-состоянием.
3. Увеличить и унифицировать контейнеры логотипов, добавить нейтральную подложку и безопасный `object-fit: contain`.
4. Согласовать отображение названия команды и имени участника с актуальными таблицами, не меняя разметку или текст.
5. Переработать визуал мест, изменения позиции, рейтинга, медалей и ФО, сохранив существующие классы и значения.
6. Устранить резкие темные поверхности, устаревшие градиенты, неравномерные отступы и скачки высоты строк.
7. Не скрывать значимые данные на узком экране без необходимости: широкая таблица получает управляемый горизонтальный scroll, а первая колонка и колонка команды могут быть закреплены CSS-средствами, если это не перекрывает остальные значения.

Один набор стилей должен корректно работать и для Ла Лиги, и для Лиги чемпионов; сезонные исключения и новые условные классы не добавляются.

### Этап 2. Адаптивность архивных лиг

- На desktop сохраняется компактная аналитическая таблица без чрезмерной ширины строк.
- На tablet уменьшаются отступы, но логотип, команда, место и итоговые очки остаются легко различимы.
- На mobile таблица не сжимается до нечитаемого состояния: пользователь явно видит возможность горизонтальной прокрутки, а закрепленные ячейки имеют непрозрачный фон и корректный `z-index`.
- Интерактивные ссылки и области наведения получают `focus-visible`, не меняя способ навигации или поведение ссылок.
- Длинные названия не ломают числовые колонки; применяется предсказуемое сокращение с ellipsis только там, где полный текст уже доступен стандартным способом браузера.

### Этап 3. Клубный чемпионат мира

После приемки архивных лиг тот же язык переносится в `cwc-page.component.scss`:

- верхняя навигация по группам, турам, общему зачету и итогам;
- групповые таблицы и внутренние рейтинги;
- карточки команд и участников;
- списки матчей и итоговые блоки;
- турнирная сетка, если она уже присутствует в legacy-шаблоне;
- горизонтальная прокрутка сложных таблиц на mobile.

Расчет групп, матчей, мест и итогов остается целиком в существующем `cwc-page.component.ts`. Даже очевидное дублирование или неудобная структура legacy-кода в рамках этого этапа не исправляются.

### Контроль неизменности данных

Так как production-код задачи должен состоять только из SCSS, проверка выполняется в двух независимых слоях:

1. **Структурное сравнение DOM:** до и после изменения совпадают заголовки, количество строк, порядок команд, текст числовых ячеек и набор доступных вкладок.
2. **Визуальное сравнение:** проверяются desktop/tablet/mobile, горизонтальная прокрутка, sticky-колонки, логотипы, длинные названия, hover и focus.

Дополнительно обязательны:

- `git diff --name-only` не содержит `.ts`, `.html`, JSON или файлов данных для этого этапа;
- production-сборка проходит без новых ошибок и без нового превышения style budget;
- прямые URL обеих архивных лиг и КЧМ открываются без ошибок консоли;
- значения матчей, таблиц, рейтинга, медалей и итоговых очков побайтно совпадают с baseline;
- визуальные изменения актуальных турниров отсутствуют.

### Критерии готовности

- архивные страницы визуально принадлежат текущему сайту, но остаются спокойнее активного сезона;
- светлые и темные логотипы читаются без ручных исключений;
- таблицы пригодны для desktop и mobile и не теряют ключевые значения;
- обе страницы на `LeaguePageComponent` выглядят единообразно;
- КЧМ использует ту же палитру и принципы после отдельного второго прохода;
- единственные production-файлы в изменении — согласованные `.scss`;
- ни один legacy-расчет, шаблон или файл данных не изменен.

## Сквозная стратегия тестирования

Для каждой функции обязательны:

1. unit-тесты domain-расчетов и сортировок;
2. runtime-валидация новых JSON-реестров;
3. проверка прямых URL и query-параметров;
4. desktop/mobile visual-check;
5. состояния с пустыми и частичными данными API;
6. production-сборка;
7. контроль 2025–26: матчи, таблицы, кубок и призовые показатели не меняются без согласованного изменения;
8. для прогнозов — тест на отсутствие утечки данных из текущего и будущих туров.

## Данные, которые потребуются от владельца проекта

Перед пунктами 4–6 потребуется собрать:

- победителей и призеров архивных Ла Лиг, Кубков, ЛЧ, КЧМ и ЧМ;
- связь старых записей с актуальными `profile.id`;
