# Roadmap развития FR Fantasy

Документ фиксирует согласованный порядок новых функций после запуска Ла Лиги 2026–27. Порядок считается приоритетным: следующая крупная функция начинается после приемки предыдущей, но общие модели данных создаются заранее, если они нужны нескольким пунктам.

## Зафиксированный порядок

1. таймлайн турниров на главной странице;
2. список участников конференции;
3. попап составов, базовый матч-центр и предматчевые котировки;
4. титулы и иконки действующих чемпионов;
5. профиль участника с историей;
6. отдельный Зал славы;
7. форма команды и история личных встреч;
8. расширение матч-центра после появления новых полей API.

## Общие архитектурные решения

### Единый каталог турниров

Главная страница, титулы, профили и Зал славы не должны иметь независимые списки соревнований. Перед реализацией таймлайна создается единый локальный каталог, например `src/assets/data/tournaments.json`.

```ts
interface TournamentCatalogItem {
  id: string;
  period: string;            // "2026–27"
  yearStart: number;
  kind: 'la-liga' | 'cup' | 'champions-league' | 'summer';
  title: string;
  route: string;
  status: 'scheduled' | 'active' | 'completed';
  startsAt?: string;
  endsAt?: string;
  logo?: string;
  source?: {
    competitionType?: string;
    seasonYear?: number;
  };
}
```

Статус завершенности должен быть явным. Нельзя определять архивность только сравнением года с текущей датой: летний турнир может закончиться, пока следующий сезон уже активен, а турнир может быть остановлен или перенесен.

Группировка выполняется по футбольному сезону:

- КЧМ-2025 завершает период 2024–25;
- ЧМ-2026 завершает период 2025–26;
- Ла Лига 2026–27 открывает период 2026–27.

### Стабильная идентичность участника

Для профилей, титулов и истории основной сущностью считается участник с `profile.id`. Название и логотип его фэнтези-команды могут меняться от сезона к сезону и хранятся как данные конкретного участия.

```ts
interface ParticipantSeasonEntry {
  profileId: string;
  tournamentId: string;
  teamId?: string;
  teamTitle: string;
  teamLogo: string;
}
```

### Исторические snapshots

Сайт не должен строить всю историю, запрашивая при каждом открытии старые внешние API. После завершения турнира создается локальный итоговый snapshot:

```text
src/assets/data/history/{tournamentId}.json
```

Он содержит участников, итоговые места, результаты H2H, ФО, кубковые результаты и призовые показатели. Для актуального турнира данные продолжают рассчитываться из API; после завершения результат фиксируется скриптом и проверяется перед переводом статуса в `completed`.

### Snapshots прогнозов

Предматчевые котировки нельзя пересчитывать задним числом по уже известным результатам. Для каждого тура до его начала сохраняется неизменяемый snapshot:

```text
src/assets/data/forecasts/{tournamentId}/tour-{tour}.json
```

Запись должна содержать идентификаторы матча и участников, время генерации, версию алгоритма, использованные туры, три вероятности исхода, ожидаемые ФО, уверенность и контрольный hash входных данных. Так опубликованный прогноз не изменится после обновления API или алгоритма.

## 1. Таймлайн турниров на главной странице

### Пользовательский сценарий

Главная страница показывает вертикальный таймлайн от новых периодов к старым. Каждый период имеет отдельный заголовок, например `2026–27`, и собственную группу турниров.

Порядок внутри периода фиксирован:

1. Ла Лига;
2. Кубок, если он разыгрывался;
3. Лига чемпионов;
4. летний турнир: КЧМ или чемпионат мира.

Турниры со статусом `active` визуально заметнее и имеют метку «Идет сейчас». `Completed` оформляются спокойнее, получают метку «Завершен» и считаются архивными. `Scheduled` можно показывать с меткой «Скоро», но без активной ссылки, пока страница не готова.

### Реализация

1. Создать типы и `TournamentCatalogService`.
2. Перенести все ссылки из `main-page.component.html` в каталог.
3. Добавить проверку уникальности `id`, корректности route, периода, статуса и порядка.
4. Построить view model: сортировка периодов по `yearStart` убыванию, турниров — по `kind`.
5. Заменить набор кнопок компонентами `TournamentTimelineComponent` и `TournamentTimelineItemComponent`.
6. Добавить desktop-таймлайн и компактную mobile-версию.
7. Для Кубка использовать ссылку на кубковую вкладку соответствующей Ла Лиги, пока у него нет отдельной страницы.

### Критерии готовности

- новый турнир добавляется одной записью каталога без правки HTML;
- периоды всегда отсортированы от нового к старому;
- внутри периода соблюдается установленный порядок;
- отсутствующий Кубок не оставляет пустого места;
- завершенные турниры отличаются от активных не только цветом, но и текстовой меткой;
- все существующие маршруты с главной страницы продолжают открываться.

## 2. Участники конференции

### Пользовательский сценарий

После сабтаба «Матчи» появляется сабтаб «Участники». Для конференции из 16 команд он показывает сетку `4 × 4`:

- крупный логотип;
- название фэнтези-команды;
- имя участника;
- ссылку на внешнюю команду, а после появления профилей — на внутренний профиль.

На узких экранах сетка становится двухколоночной, затем одноколоночной. Порядок участников должен совпадать с порядком в конфигурации конференции, а не с текущей таблицей.

### Реализация

1. Зарезервировать `confTabId = 4`.
2. Создать standalone-компонент `ConferenceParticipantsComponent`.
3. Передавать в него `stage.leagues[confId].profiles` и общий индекс профилей.
4. Выделить переиспользуемый `ParticipantCardComponent`, который затем используется в профиле и Зале славы.
5. Добавить пустое состояние и проверку отсутствующих профилей/логотипов.

### Критерии готовности

- в каждой конференции отображаются ровно ее 16 участников без дублей;
- desktop-сетка имеет четыре колонки;
- подписи не перекрывают логотипы и корректно сокращаются;
- смена конференции обновляет список без дополнительного запроса API;
- прямой URL с `confTabId=4` восстанавливает выбранный экран.

## 3. Попап составов, базовый матч-центр и котировки

### Первая версия матч-центра

Клик по сопернику в расписании или по матчу открывает модальное окно. Оно показывает:

- хозяев и гостей, счет или время начала;
- основной состав и запас обеих команд;
- капитана и вице-капитана;
- позиции, стоимость и реальный клуб футболиста;
- общую стоимость состава;
- предматчевые вероятности исходов;
- статус прогноза: предварительный, зафиксированный или результат известен.

Модальное окно должно поддерживать клавиатуру, закрытие по `Escape`, возврат фокуса и блокировку прокрутки фона.

### Источники данных

- `full_info.data.players[profileId].team.rosters_by_tour[tour]` — основа, запас, капитан и вице-капитан;
- `sport_players_tour_stat` — имя футболиста, позиция, `team_id`, цена, `score` и `match_time`;
- локальный справочник реальных клубов — название и эмблема;
- forecast snapshot — опубликованные до тура котировки.

Загрузка подробностей должна быть ленивой: страница турнира не обязана заранее строить карточки всех футболистов. Нужен `MatchCenterFacade` с кэшем по ключу `competition + season + tour`.

### Алгоритм котировок первой версии

Для матча тура `N` запрещено использовать данные тура `N` и более поздних туров. Входными данными служат:

- взвешенные ФО последних доступных туров;
- текущий рейтинг формы;
- разброс ФО как показатель стабильности;
- правило ничьей `drawGap` конкретного соревнования;
- нейтральный prior при недостатке истории.

Первую версию лучше реализовать объяснимой симуляцией распределений, а не непрозрачной ML-моделью. Результат: три вероятности, сумма которых равна 100%. Рядом показываются факторы прогноза и уровень уверенности.

Перед началом тура запускается скрипт генерации snapshot. После начала тура существующий файл не перезаписывается без явного флага и проверки.

### Реальные клубы, эмблемы и флаги

Текущий API проверен на Ла Лиге 2026: футболист содержит только поля `id`, `name`, `amplua_id`, `team_id`, `cost`, `stat_by_tours`. Национальности, флага и эмблемы клуба нет.

Следовательно:

- **эмблемы реальных клубов нужно подтянуть и хранить отдельно** в версионируемом справочнике по `team_id`; это рекомендуется сделать для первой версии матч-центра;
- текущий `teams.json` можно использовать как основу структуры, но он относится к старому составу Ла Лиги, а `logo` в нем пустой; его нужно заменить сезонным справочником;
- **флаги стран также потребуют отдельного источника**, причем API не дает даже nationality id, поэтому понадобится внешний справочник `player id → страна`;
- флаги предлагается отложить: они менее важны для чтения состава и заметно дороже в сопровождении, чем 20 клубных эмблем.

Рекомендуемый scope первой версии: позиция + имя + клубная эмблема, без флага страны.

### Критерии готовности

- попап открывается из расписания и списка матчей;
- состав соответствует `rosters_by_tour` выбранного тура;
- капитан и запас визуально различимы;
- отсутствие футболиста в справочнике не ломает окно;
- прогноз не использует данные текущего или будущего тура;
- историческая котировка не меняется после результата матча;
- вероятности валидны и в сумме дают 100%;
- для первого тура предусмотрен честный нейтральный прогноз и низкая уверенность.

## 4. Титулы и иконки действующих чемпионов

### Модель данных

Результаты турниров хранятся отдельно от отображения иконок:

```ts
interface TournamentPlacement {
  tournamentId: string;
  profileId: string;
  place: 1 | 2 | 3;
  titleType: 'league' | 'cup' | 'champions-league' | 'world-cup' | 'club-world-cup';
}
```

Действующий чемпион определяется как победитель последнего завершенного турнира данного `titleType`. Это вычисляемое состояние, а не вручную проставленный флаг у участника.

### Отображение и реализация

1. Создать реестр типов титулов и их иконок.
2. Наполнить результаты завершенных турниров; неизвестные архивные результаты запросить у владельца проекта.
3. Создать `AchievementService` и переиспользуемый `TitleBadgeComponent`.
4. Показывать небольшую иконку возле логотипа в таблице, участниках и матчах, с tooltip названия и сезона.
5. Несколько действующих титулов объединять в компактную группу; полный список показывать в профиле.
6. После завершения нового турнира действующего чемпиона определять автоматически по каталогу.

## 5. Профиль участника с историей

Маршрут: `/participants/:profileId`.

Страница содержит имя и актуальную команду, прошлые названия и логотипы, титулы, участия по сезонам, итоговые места, H2H-баланс, ФО, кубковые достижения, специальные призы и ссылки на матчи.

### Реализация

1. Создать глобальный индекс участников по `profile.id`.
2. Написать build-скрипт, агрегирующий сезонные файлы и исторические snapshots.
3. Создать `ParticipantHistoryService` и standalone-страницу профиля.
4. Не загружать все внешние API прошлых сезонов при каждом открытии.
5. Постепенно заменить ссылки на внешнюю команду внутренними ссылками на профиль, сохранив внешнюю ссылку отдельной кнопкой.

### Критерии готовности

- смена названия команды не создает нового участника;
- один профиль объединяет Ла Лигу, Кубок, ЛЧ и летние турниры;
- отсутствующие старые показатели показываются как «нет данных», а не как ноль;
- страница доступна по прямой ссылке после обновления браузера.

## 6. Зал славы

Отдельный маршрут `/hall-of-fame` показывает победителей и призеров, фильтры по соревнованию и периоду, количество чемпионств/финалов/призовых мест и действующих чемпионов.

Зал славы использует тот же `TournamentPlacement` и snapshots, что титулы и профили. Второй ручной список победителей создавать нельзя. Для архивных результатов, которых нет в локальных файлах, нужен однократный импорт данных от владельца проекта.

Критерий готовности: новый завершенный snapshot появляется в Зале славы без правки компонента, а каждый титул одинаково отображается в Зале славы и профиле.

## 7. Форма и история личных встреч

### Форма

- последние пять H2H-результатов;
- средние набранные и пропущенные ФО;
- серии побед и без поражений;
- изменение рейтинга;
- стабильность результатов;
- форма по выбранному турниру и общая форма, если данные сопоставимы.

### Личные встречи

- количество матчей, побед, ничьих и поражений;
- суммарные и средние ФО;
- крупнейшая победа;
- последние встречи по датам;
- разбивка по турнирам и стадиям.

Для реализации выделяются `FormCalculator` и `HeadToHeadHistoryService`. Актуальные данные берутся из view model, прошлые — из snapshots. Компактный блок показывается в матч-центре, расширенный — в профиле. Эти же показатели позднее используются прогнозной моделью.

## 8. Расширение матч-центра после обновления API

Функция начинается после появления подтвержденного контракта API для признака участия футболиста и начисленных ему очков.

Планируемое отображение:

- индивидуальные ФО и сыгранные минуты;
- статус «не вышел»;
- признак учета в результате фэнтези-команды;
- вклад игрока и капитанский множитель;
- фактические замены основы и скамейки;
- сравнение прогноза с результатом;
- состояние live/incomplete/final.

Новые поля сначала добавляются как optional в API-модель. Adapter переводит внешний контракт во внутреннюю модель матч-центра, а UI включает блоки по наличию capability, а не по номеру сезона. Старые сезоны должны продолжить работать без новых полей.

## Сквозная стратегия тестирования

Для каждой функции обязательны:

1. unit-тесты domain-расчетов и сортировок;
2. runtime-валидация новых JSON-реестров;
3. проверка прямых URL и query-параметров;
4. desktop/mobile visual-check;
5. состояния с пустыми и частичными данными API;
6. production-сборка;
7. контроль 2025–26: матчи, таблицы, кубок и призовые показатели не меняются без согласованного изменения;
8. для прогнозов — тест на отсутствие утечки данных из текущего и будущих туров.

## Данные, которые потребуются от владельца проекта

Перед пунктами 4–6 потребуется собрать:

- победителей и призеров архивных Ла Лиг, Кубков, ЛЧ, КЧМ и ЧМ;
- связь старых записей с актуальными `profile.id`;
- случаи совместных или командных победителей;
- желаемые иконки типов титулов либо разрешение подготовить единый комплект;
- подтверждение состава турниров и статусов для первого каталога главной страницы.

Перед пунктом 3 нужно принять одно визуальное решение: рекомендуемый вариант — отдельно добавить эмблемы реальных клубов Ла Лиги и пока не добавлять флаги стран футболистов.
