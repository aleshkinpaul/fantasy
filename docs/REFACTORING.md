# Рефакторинг и технический долг

## Текущее состояние

Основной рефакторинг актуального контура выполнен в августе 2026 года. Разделы ниже сохраняют исходный аудит и объясняют принятые решения; замечания про архивные `LeaguePageComponent` и `CWCPageComponent` по-прежнему актуальны.

Фактическое состояние актуальных турниров:

- `LeagueH2HPageComponent` сокращен примерно до 260 строк и не использует `@ts-nocheck`;
- загрузка API сосредоточена в `CompetitionDataLoaderService`;
- объединение этапов ЛЧ выполняет `competition-stages.merger.ts` без мутации исходных ответов;
- `CompetitionFacade` возвращает готовую view model;
- H2H, таблицы, места, рейтинг, кубок, специальные показатели и призы разделены по domain-модулям;
- сезонные id находятся в `competition-rules.registry.ts` и выбираются через `rulesId`;
- активная страница отменяет загрузку при уничтожении компонента и показывает ошибку с ручным повтором;
- `LeagueH2HDataService` и расчет рейтинга типизированы через domain/API-модели; базовые правила `drawGap`, подсчета замен и legacy-медианы закреплены unit-тестами;
- `npm run verify:season-2025` защищает матчи, таблицы, кубок, призы, составы и профили трех турниров.

Архивные компоненты не рефакторились намеренно. Данные актуальных турниров разделены по сезону и соревнованию; следующие задачи — дополнительные unit/UI-тесты и дальнейшая типизация domain-слоя.

## Основные риски

### Смешение обязанностей

Риск устранен в актуальном контуре через loader, facade и domain-модули. Он сохраняется в архивных страницах.

### Слабая типизация

API и конфигурация актуального контура типизированы, а обязательные связи проверяет runtime validator. В prize-стратегиях и части view model еще остается `any`; глобальный strict mode пока не включен.

### Дублирование

Расчет рейтинга, медалей, мест, median/min/max и статистики составов повторяется в трех страницах. Исправление может попасть только в одну реализацию.

### Сезонные значения в коде

Profile/player/team id и лимиты замен перенесены в registry сезонных правил. Соответствие numeric prize id формулам пока остается в domain-коде и требует отдельной стратегии при изменении регламента.

### Мутация входных данных

До рефакторинга компоненты дописывали поля в объекты API и `consts.json`: score/result матчей, rating команды, runtime-поля профиля, nominees. В актуальном контуре объединение API выполняется без мутации входов, а вычисления изолированы в facade/domain; часть runtime view model всё ещё изменяется в рамках одной загрузки.

### Сетевой слой

- актуальная страница использует один subscription к facade; отмена при уничтожении компонента пока не добавлена;
- прямые запросы к внешнему домену зависят от CORS;
- нет timeout/retry/cache/fallback;
- loader с boolean некорректен для нескольких параллельных запросов;
- часть error callbacks пустая.

### Контракт URL

Без `?year=` страницы обращаются к отсутствующему разделу profiles. Невалидный год или несовпавший `type` заканчивается runtime error вместо понятного сообщения.

### Конфигурация как монолит

До разбиения большой `consts.json` было трудно обозревать и проверять, а `matches` и `schedule` дублировали календарь. Теперь актуальные турниры разделены по файлам и используют только `matches`; оставшийся долг — связь prize id со стратегиями расчета.

### Тесты

Добавлен browser-level characterization harness с локальными API fixtures и SHA-256 golden-файлами сезона 2025–26. Unit-тестов отдельных граничных формул пока недостаточно.

## Целевая структура

```text
core/
├── api/               типизированный FantasyH2hClient
├── config/            загрузка и валидация SeasonConfig
└── models/            API DTO и domain models

features/competition/
├── data/              CompetitionFacade, объединение этапов
├── domain/            H2H, standings, rating, medals, cup
├── prizes/            стратегии призов
└── ui/                page + презентационные компоненты

features/cwc/
├── domain/            командные матчи и play-off
└── ui/
```

Главный принцип: API DTO не мутируется. После загрузки создается нормализованная доменная модель, а UI получает готовую immutable view model.

## Рекомендуемая последовательность

### Этап 0. Зафиксировать поведение

- сохранить маленькие анонимизированные fixtures двух API;
- написать golden tests для таблиц сезона 2025–26;
- покрыть `drawGap`, переход этапов, кубок и два API ЛЧ;
- зафиксировать ожидаемых лидеров нескольких призов.

Без этого глубокий рефакторинг расчетов трудно отличить от изменения регламента.

### Этап 1. Описать контракты

- разделить `FullInfoResponse`, `TourStatResponse`, `SeasonConfig` и runtime view models;
- убрать дублирующий `ILeague` в двух model-файлах;
- явно задать string/number преобразования на границе API;
- добавить runtime validator конфигурации.

### Этап 2. Выделить загрузку

Создать `CompetitionDataFacade`, который принимает `(competitionType, yearStart)` и возвращает одно состояние:

```ts
type LoadState<T> =
  | { status: "loading" }
  | { status: "ready"; data: T }
  | { status: "error"; message: string };
```

Facade должен выбрать конфигурацию, валидировать profiles, загрузить этапы, нормализовать строковые числа, объединить этапы без мутации и централизованно обработать ошибки.

### Этап 3. Выделить чистую доменную логику

Перенести в функции/сервисы без Angular-зависимостей:

- `calculateMatch`;
- `calculateStandings` с явными tie-breakers;
- `calculateStageStats`;
- `calculateCupStats`;
- `calculateMedals` и `calculateRating`;
- `calculateTransfers`;
- командный формат КЧМ.

### Этап 4. Конфигурировать правила сезона

Вместо проверок route и tour index в коде описать:

```ts
interface CompetitionRules {
  drawGap: number;
  playoffDrawGap: number;
  substitutionsByTour: Record<number, number>;
  standingsTieBreakers: string[];
  specialEntities: Record<string, string | string[]>;
}
```

Призы лучше реализовать как registry стратегий с понятными ключами, а не связывать поведение с numeric id.

### Этап 5. Разделить UI

Оставить page-компоненту только чтение route/query state, вызов facade, выбор вкладок и передачу готовых данных презентационным компонентам.

### Этап 6. Разделить сезонные файлы

```text
assets/data/seasons/
├── 2025-26/
│   ├── spain.json
│   ├── champions-league.json
│   └── world-cup.json
└── 2026-27/
    ├── spain.json
    └── champions-league.json
```

Loader строит путь к нужному файлу из `type` и `yearStart`, поэтому manifest не требуется. `matches` является единственным источником календаря для вкладок матчей и расписания; производный `schedule` не хранится.

## Быстрые улучшения с малым риском

1. добавить route guard/default year и страницу ошибки конфигурации;
2. заполнить HTTP error states архивных страниц;
3. перенести fallback icons в сезонно-независимый каталог;
4. добавить скрипт валидации JSON и assets;
5. удалить/архивировать `.scss.clean`, `.backup`, `.temp` после проверки актуальных файлов;
6. настроить formatter/linter и постепенно убрать `@ts-nocheck` из архивных страниц.

## Критерии завершения рефакторинга

- новый сезон добавляется config/profile/assets без изменения расчетных компонентов;
- все внешние ответы типизированы и проверяются на границе;
- нет `@ts-nocheck` в страницах турниров;
- доменные правила имеют unit-тесты;
- при недоступном API пользователь видит понятную ошибку;
- смена сезона не сохраняет мутированное состояние;
- build и тесты проходят без warnings, связанных с бюджетами и типами.
