# Рефакторинг и технический долг

## Текущее состояние

Проект работает как быстро развивавшийся турнирный dashboard: большая часть бизнес-логики появилась непосредственно в компонентах вместе с конкретными регламентами. Это удобно для разового изменения сезона, но делает новый сезон зависимым от скрытых условий и hard-coded id.

Главные размеры текущего кода:

- `LeagueH2HPageComponent` — около 1400 строк TypeScript и крупный HTML-шаблон;
- `CWCPageComponent` — около 780 строк TypeScript;
- `LeaguePageComponent` — около 500 строк TypeScript;
- `consts.json` — около 240 KB регламентов и календарей;
- три основных компонента отключают type checking через `// @ts-nocheck`.

В репозитории уже присутствуют незакоммиченные изменения предыдущего рефакторинга, включая удаление старой GraphQL-интеграции Sports.ru и частичное выделение сервисов. Любая следующая работа должна сохранять эти изменения и начинаться с просмотра `git diff`.

## Основные риски

### Смешение обязанностей

`LeagueH2HPageComponent` одновременно выполняет HTTP, нормализацию, доменные расчеты, состояние вкладок и подготовку view model. Ошибка в одном сезонном правиле способна нарушить загрузку всей страницы.

### Слабая типизация

Фактические данные шире интерфейсов `domain.ts` и `model.ts`. Используются `any`, неописанные поля и строковые числа. `@ts-nocheck` скрывает обращения к отсутствующим участникам, турам и roster.

### Дублирование

Расчет рейтинга, медалей, мест, median/min/max и статистики составов повторяется в трех страницах. Исправление может попасть только в одну реализацию.

### Сезонные значения в коде

ID участников, футболистов, клубов, лимиты замен и формулы призов зашиты в TypeScript. Простое копирование JSON для 2026–27 не гарантирует правильный результат.

### Мутация входных данных

Компоненты дописывают поля в объекты API и `consts.json`: score/result матчей, rating команды, runtime-поля профиля, nominees. При повторной обработке или смене сезона это может дать накопительный эффект.

### Сетевой слой

- вложенные `subscribe` усложняют отмену запросов и error handling;
- прямые запросы к внешнему домену зависят от CORS;
- нет timeout/retry/cache/fallback;
- loader с boolean некорректен для нескольких параллельных запросов;
- часть error callbacks пустая.

### Контракт URL

Без `?year=` страницы обращаются к отсутствующему разделу profiles. Невалидный год или несовпавший `type` заканчивается runtime error вместо понятного сообщения.

### Конфигурация как монолит

Большой `consts.json` трудно обозревать и проверять. `matches` и `schedule` дублируют календарь, а prize id связан с цепочкой условий в компоненте.

### Недостаток тестов

Есть только минимальные spec-файлы. Ключевые правила H2H, ничьей, таблиц, этапов, кубка и призов не защищены регрессией.

## Целевая структура

```text
core/
├── api/               типизированный FantasyH2hClient
├── config/            загрузка и валидация SeasonConfig
└── models/            API DTO и domain models

features/competition/
├── data/              CompetitionFacade, объединение этапов
├── domain/            H2H, standings, rating, medals, cup
├── prizes/            стратегии призов
└── ui/                page + презентационные компоненты

features/cwc/
├── domain/            командные матчи и play-off
└── ui/
```

Главный принцип: API DTO не мутируется. После загрузки создается нормализованная доменная модель, а UI получает готовую immutable view model.

## Рекомендуемая последовательность

### Этап 0. Зафиксировать поведение

- сохранить маленькие анонимизированные fixtures двух API;
- написать golden tests для таблиц сезона 2025–26;
- покрыть `drawGap`, переход этапов, кубок и два API ЛЧ;
- зафиксировать ожидаемых лидеров нескольких призов.

Без этого глубокий рефакторинг расчетов трудно отличить от изменения регламента.

### Этап 1. Описать контракты

- разделить `FullInfoResponse`, `TourStatResponse`, `SeasonConfig` и runtime view models;
- убрать дублирующий `ILeague` в двух model-файлах;
- явно задать string/number преобразования на границе API;
- добавить runtime validator конфигурации.

### Этап 2. Выделить загрузку

Создать `CompetitionDataFacade`, который принимает `(competitionType, yearStart)` и возвращает одно состояние:

```ts
type LoadState<T> =
  | { status: "loading" }
  | { status: "ready"; data: T }
  | { status: "error"; message: string };
```

Facade должен выбрать конфигурацию, валидировать profiles, загрузить этапы, нормализовать строковые числа, объединить этапы без мутации и централизованно обработать ошибки.

### Этап 3. Выделить чистую доменную логику

Перенести в функции/сервисы без Angular-зависимостей:

- `calculateMatch`;
- `calculateStandings` с явными tie-breakers;
- `calculateStageStats`;
- `calculateCupStats`;
- `calculateMedals` и `calculateRating`;
- `calculateTransfers`;
- командный формат КЧМ.

### Этап 4. Конфигурировать правила сезона

Вместо проверок route и tour index в коде описать:

```ts
interface CompetitionRules {
  drawGap: number;
  playoffDrawGap: number;
  substitutionsByTour: Record<number, number>;
  standingsTieBreakers: string[];
  specialEntities: Record<string, string | string[]>;
}
```

Призы лучше реализовать как registry стратегий с понятными ключами, а не связывать поведение с numeric id.

### Этап 5. Разделить UI

Оставить page-компоненту только чтение route/query state, вызов facade, выбор вкладок и передачу готовых данных презентационным компонентам.

### Этап 6. Разделить сезонные файлы

```text
assets/data/seasons/
├── 2025-26/
│   ├── spain.json
│   ├── champions-league.json
│   └── world-cup.json
└── 2026-27/
    ├── spain.json
    └── champions-league.json
```

Можно добавить index manifest для поиска нужного файла. Генератор календаря должен строить и `matches`, и производный `schedule`.

## Критерии завершения рефакторинга

- новый сезон добавляется config/profile/assets без изменения расчетных компонентов;
- все внешние ответы типизированы и проверяются на границе;
- нет `@ts-nocheck` в страницах турниров;
- доменные правила имеют unit-тесты;
- при недоступном API пользователь видит понятную ошибку;
- смена сезона не сохраняет мутированное состояние;
- build и тесты проходят без warnings, связанных с бюджетами и типами.
